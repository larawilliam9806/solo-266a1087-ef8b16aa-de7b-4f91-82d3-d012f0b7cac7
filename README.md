# 潮位越线回查

港口值班复盘工具：按批上传单站**预报**与**实测** CSV，在高潮位越线后回查
值班端**提前多久**收到了**持续有效**的预警。

- 后端：Flask 3 + SQLite（WAL）
- 前端：服务端渲染，无需构建
- 部署：`docker compose up --build` 一条命令启动

## 业务口径

| 事项 | 口径 |
| --- | --- |
| 时刻 | 全部 **UTC**。整点字段必须分秒为 0；带 `Z` 或 `+00:00` 均可，其它时区偏移会被拒绝 |
| 潮位 | **厘米**（cm），实数 |
| 越线 | 上一小时**低于**警戒水位，本小时**达到或高于**警戒水位 |
| 待核 | 本小时达线、但上一小时缺测 → 标为「待核」，不计算提前量 |
| 回查报文 | 只读取**目标整点**为这些越线整点的预报报文，其它目标一概不读 |
| 值班端权威 | 越线前每一刻，以**当时已收到的最新签发**报文为准；迟到的旧报文不改变结论 |
| 计时起点 | 首次达成持续有效（潮位 ≥ 警戒）的报文 **接收时刻**；中途跌破警戒即取消；再次达线重新起算 |
| 提前分钟 | 越线整点 − 计时起点的接收时刻（整点时刻本身收到的报文计 0 分钟） |
| 资料快照 | 每次回查在**一个写事务**内冻结预报与实测并落库；回查期间可继续补档，但**不改变已提交的回查** |
| 上传原子性 | 预报与实测两表**一起校验、同一事务一起生效**；任一行不合法则整批不写入 |

## 快速开始（Docker）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

数据存放在命名卷 `tide-data` 的 `/data/tide.db`，`docker compose down` 不会丢失；
需要清空时执行 `docker compose down -v`。

自定义端口与密钥：

```bash
PORT=9000 SECRET_KEY='换成随机长串' docker compose up -d --build
```

## 本机运行（不使用 Docker）

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt pytest
python -m app                       # http://127.0.0.1:5000
# 或指定库文件
DATABASE_PATH=instance/tide.db python -m app
```

## 使用流程

1. **上传**：填已建档站号，或新建站号；勾选预报 / 实测 CSV（可只传一张）。
2. **发起回查**：选择站号、时段（UTC 整点，含首尾）、警戒水位（cm），提交。
3. **查看结果**：每个越线整点一行——判定（越线 / 待核）、上一小时与本小时实测、
   是否持续有效预警、起报接收时刻、提前分钟、越线前最新预报、文字说明。
   - 无有效预警的整点同样列出，并说明是「报文低于警戒」还是「未收到报文」。
   - 「逐时预警生效过程」展开可见每条已接收报文的计时影响（开始/持续/取消）。
   - 可导出 CSV。
4. **补档**：回查期间可继续上传订正；对**已提交**的回查无影响，新建回查才会用到新资料。

### CSV 格式

预报 `forecast.csv`（同一站）：

```csv
目标整点,签发时刻,接收时刻,潮位
2026-05-01 05:00,2026-04-30 20:00,2026-04-30 20:04,182
2026-05-01 05:00,2026-04-30 23:30,2026-04-30 23:33,195
```

实测 `observation.csv`：

```csv
整点,潮位
2026-05-01 04:00,148
2026-05-01 05:00,186
```

- 表头中英文别名均可（如 `target_utc,issued_utc,received_utc,level_cm`；
  `hour_utc,level_cm`），也支持 `站号/station` 列（须与本批站号一致）。
- 时刻接受 `YYYY-MM-DD HH:MM[:SS]`、`YYYY-MM-DDTHH:MM[:SS]`，以及紧凑写法
  `YYYYMMDDHH` / `YYYYMMDDHHMM` / `YYYYMMDDHHMMSS`（按长度消歧，10 位即到小时）。
- 分隔符支持逗号、分号、制表符；编码支持 UTF-8（含 BOM）与 GB18030。
- **同一目标整点的签发时刻唯一**：重复 `(目标, 签发)` 直接拒绝。
  再次上传相同的 `(目标, 签发)` 视为对潮位/接收时刻的更新。
- **同一整点可订正**：实测以最新上传为准覆盖（单文件内同一整点重复则拒绝）。
- 接收时刻不得早于签发时刻。

`samples/` 下有可直接上传的示例文件。

## 测试

```bash
python -m pytest -q
```

迟到旧报文不得覆盖新签发、越线后收到的报文不计入、时段首尾包含、

## 说明与取舍

- 时区不做隐式换算：非 UTC 偏移直接报错，避免"看起来对、实际差 8 小时"。
- gunicorn 固定**单 worker、多线程**，配合 SQLite WAL 与 `BEGIN IMMEDIATE`，
  保证回查冻结的原子性与一致性（多 worker 写库会放大锁竞争）。
- 回查快照按需只保存：时段前后各一小时实测、目标为越线整点的预报报文。
  已提交回查的展示完全来自 `review_*` 表，与主表后续变化无关。
